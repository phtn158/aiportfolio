Personal Finance Coach & Spending Analyzer

Started as a JHU case study for a fictional fintech (ClearLedger Inc.); now being repositioned as a ThuWork product demonstration — a finance coach that turns a messy bank-statement CSV into categorized spending, a days-to-limit forecast, ranked optional savings scenarios, and a coach that answers follow-ups using only the user's own analyzed data.

Tools: Python · Streamlit · pandas · Plotly · scikit-learn (regression forecast) · LLM API (few-shot categorization, with rules fallback) · Streamlit Community Cloud (proposed hosting)

📄 PRD 📄 Spec 🔒 Privacy & security requirements 💻 Repo + Add demo

The Problem

Case-study brief: ClearLedger Inc., a pre-Series-A fintech with 55,000 users, was losing 71% of users after their second session because the app required manually tagging 60–150 transactions before delivering any insight. The assignment: design a Personal Finance Coach that eliminates that manual step entirely, under real constraints — limited ML expertise, no labeled training data, and a strict cost budget — while getting a user to their first real insight in under five minutes.

My Role & Approach

Product thinking

Scoped the build around four AI capabilities that had to work as one coherent pipeline rather than isolated exercises: LLM classification, interactive visualization, regression-based prediction, and stateful conversational memory. Every design choice (few-shot prompts instead of a trained classifier, per-user regression instead of a cross-user model) was made to work around the "no labeled data / limited ML expertise" constraints, not just picked for its own sake.

Build approach

Ingests and normalizes a raw transactions CSV, enriches it with MCC-code categories, then re-classifies each transaction into a small fixed taxonomy via a few-shot LLM prompt (batched/cached by merchant to control cost). That feeds an analytics layer (spend aggregation + z-score anomaly detection) which powers both a live spending dashboard and a per-user regression model predicting days remaining until the user's self-set discretionary limit. Ranked, category-level spending-reduction suggestions and the prediction are then grounded into a multi-turn conversational coach via system-prompt injection, so the coach cites real numbers instead of inventing them.

What It Does — v2 PRD stage, rebuild in progress

  • Ingests a bank-statement CSV and categorizes every transaction with an LLM — no manual tagging required
  • Renders an interactive spending dashboard (category breakdown, spend trend, anomaly markers, limit burn-down)
  • Predicts days remaining before the user hits their discretionary spending limit, via a regression model trained on their own transaction history
  • Surfaces ranked, category-level suggestions for extending that runway (e.g. "cutting dining 20% adds 2 days")
  • Answers follow-up questions through a multi-turn conversational coach grounded in the actual prediction and spend data
  • v2 additions in the PRD: unusual-charge alerts, a subscription/cancellation shortlist, and per-persona synthetic demo datasets (early-career professional, variable-income freelancer, household budgeter)

Repositioning as a Portfolio Product

The v2 rewrite (PRD Draft v2, Oct 2026) reframes the project for two audiences — ThuWork agency prospects and AI product hiring managers — and adds the guardrails a shareable demo needs: every category, forecast, and coach answer shows its basis and uncertainty; forecasts use chronological backtesting against a simple baseline; the public demo runs only on approved synthetic data; card data (PAN/CVV) is never loaded into the coach; and API keys live in the host's secret manager, never the repo. A separate privacy & security requirements doc covers data classification, LLM-provider rules, retention, and a release checklist.

Aspect-Based Sentiment Classification

An ABSC pipeline that classifies sentiment toward specific aspects of a review (e.g. food vs. service) via LLM prompting through LangChain, rather than training a task-specific classifier — benchmarked on the SemEval-2014 Task 4 dataset.

Tools: Python · LangChain · Hugging Face Transformers (Qwen2.5-0.5B-Instruct) · pandas · scikit-learn · SemEval-2014 laptop/restaurant review dataset

📄 Spec 💻 Repo / README + Add demo

The Problem

Aspect-Based Sentiment Classification identifies sentiment toward individual aspects within a piece of text rather than one overall label — e.g. in "the food was delicious, but the service was slow," sentiment toward food is positive while service is negative. That level of detail is far more actionable for businesses than document-level sentiment. ABSC is traditionally handled with fine-tuned classifiers (BERT-style models); this project instead explores how far a general-purpose LLM, driven purely by prompt design, can get on the same task.

My Role & Approach

Product thinking

Chose a small, locally-run instruction-tuned model (Qwen2.5-0.5B-Instruct) over a larger one deliberately — the exercise's goal was understanding how each pipeline component works end-to-end, not maximizing accuracy, so faster iteration won out over model size.

Build approach

Wrapped a Hugging Face text-generation pipeline in LangChain's HuggingFacePipeline, paired it with a few-shot PromptTemplate that constrains output to a fixed sentiment label set, and built a custom output parser (regex extraction + ast.literal_eval, wrapped in a RunnableLambda) to safely pull clean (aspect, sentiment) tuples out of noisy raw generations. The three pieces are composed into a single chain with LangChain's pipe operator.

What It Does — in progress

  • Loads and validates the SemEval-2014 laptop and restaurant review datasets
  • Runs a few-shot prompt through the LangChain chain to extract aspects and classify sentiment (positive/negative/neutral/conflict) per aspect
  • Parses raw LLM output into clean, validated (aspect, sentiment) tuples
  • Iterates over the deduped review set with progress tracking (tqdm), collecting predictions per review

Still to build: graceful handling of failed/unparseable generations, attaching gold labels alongside predictions, and the scikit-learn evaluation layer (precision/recall/F1, confusion matrix) that scores the pipeline against ground truth.

CI/CD Failure Log Intelligence

A prompt-engineering pipeline that reads a failed CI/CD build log, sanitizes it, classifies the failure, and explains it in plain English with a concrete fix — evaluated with an LLM-as-judge instead of word-overlap metrics.

Tools: Python · Prompt engineering · PII sanitization · LLM-as-judge evaluation (+ ROUGE / BERTScore)

+ Add spec 💻 Repo + Add demo

The Problem

CI/CD pipelines fail across many different tools — Jenkins, GitHub Actions, GitLab CI, CircleCI, Azure DevOps — each producing noisy, inconsistently formatted logs. Engineers lose time just figuring out what broke before they can even start fixing it. The goal: cut time-to-diagnosis to under five minutes by having an LLM read the failed-build log and explain it, without ever exposing raw log contents (which can contain secrets/PII) directly to the model.

My Role & Approach

Product thinking

Set hard rules up front rather than letting the LLM free-form: raw logs are never sent to the model unsanitized, classification must use only a fixed label set, and summaries must follow a fixed output structure — so results stay consistent and machine-parseable across the whole dataset. Judged usefulness by task metrics (accuracy, actionability) rather than word-overlap metrics, since a technically-similar-sounding summary isn't the same as a useful one.

Build approach

Built a pipeline that sanitizes each raw log first (strips long token-like strings, file paths, and KEY=VALUE env-var secrets), classifies the failure against a fixed taxonomy with a majority-vote consistency check across repeated model calls, then generates a plain-English summary with a concrete fix. An LLM-as-judge scores each summary for accuracy and actionability alongside ROUGE/BERTScore, and a separate script automatically reruns and regenerates any summary the judge flags as not actionable.

What It Does

  • Ingests failure logs from a multi-CI-tool dataset (Jenkins, GitHub Actions, GitLab CI, CircleCI, Azure DevOps)
  • Sanitizes each log — strips tokens, file paths, and env-var secrets — before anything reaches the model
  • Classifies each failure into a fixed label set, with a consistency check across repeated model calls
  • Summarizes the failure in plain English with a concrete suggested fix, in a fixed output structure
  • Scores summary quality with an LLM-as-judge (accuracy + actionability) alongside ROUGE/BERTScore
  • Automatically reruns and regenerates summaries the judge flags as low-actionability

Outcome

Ran end-to-end across the failure-log dataset, producing judged accuracy/actionability scores and ROUGE/BERTScore metrics per sample.

Applied GenAI Study Hub

A personal study site — dictionary, spaced-repetition flashcards, quizzes, a formula/code reference, and a weak-spot dashboard — built from the lecture slides of an Applied Generative AI program, organized around what you'd actually do with the material rather than the order it was taught in.

Tools: HTML/CSS/JavaScript (ES modules, no framework) · localStorage (SM-2-style spaced repetition) · Python (PDF-to-content pipeline, content validation)

📄 Spec 📝 Build notes 🔗 Live site

The Problem

Studying from a stack of lecture-slide PDFs doesn't build retention — concepts are scattered across multiple decks, formats are inconsistent, and there's no mechanism for noticing what you keep getting wrong. This project turns those PDFs into one structured, testable, self-updating study surface for a single learner (me) working through an Applied Generative AI program, meant for reviewing and self-testing between lectures on a phone or laptop without setting up an account anywhere.

My Role & Approach

Product thinking

Deliberately scoped out accounts, login, multi-device sync, and any runtime LLM calls — all dictionary, flashcard, and quiz content is authored once from source material and stored statically, since the real requirement is one learner reviewing on whatever device they're on right now, not a multi-user product. The content structure itself went through revision: mirroring the program's actual lecture order first felt logical but read like a syllabus, so it was reorganized task-flow-first — six repeatable task-type modules (Classification, Summarization, QA, Translation, Code Generation, Speech-to-Text), each following the same pattern, with shared prerequisites up front and cross-cutting/reference material pushed to the end.

Build approach

Static HTML/CSS/JS with no build step; a single content.json is the source of truth that every view (dictionary, flashcards, quiz, formulas, dashboard) renders from, so adding a concept automatically makes it searchable and flashcard-eligible without per-view wiring. Chose a simplified SM-2 spaced-repetition algorithm (the same family Anki uses) over a binary right/wrong toggle so the app can track an ease factor and miss count per card and actually prioritize what needs review. The content pipeline extracts new lecture PDFs with pdftotext, then hand-authors entries into the shared schema, validated by script for duplicate IDs and valid quiz answer indices before merging.

What It Does

  • Dictionary of every concept from the program (181 entries as of the latest update), each with a plain-language "explain like I forgot everything" one-liner above the formal definition, tagged by category and by the Python package that implements it
  • Flashcards with SM-2-style spaced repetition — cards marked "Missed it" or "Shaky" resurface more often; consistently-correct cards space out further
  • Multiple-choice quizzes per module, with an explanation shown after each answer
  • A formulas & code reference pulling every formula into one lookup page
  • A "My Progress" weak-spot dashboard aggregating flashcard and quiz misses into a focus list
  • Site-wide search, and a weekly scheduled workflow that checks for new lecture material and proposes dictionary/flashcard/quiz additions in the existing schema

Outcome So Far

Currently 181 dictionary entries, 92 flashcards, and 64 quiz questions across 13 modules, spanning the original NLP/LLM curriculum, a Claude-specific practitioner track, and a newly-added Retrieval-Augmented Generation (RAG) module (fundamentals, RAGAs evaluation, optimization levers, and multimodal RAG) — all folded in through the weekly content-update workflow. Since a real browser wasn't available in the build environment, the app was tested by running its actual ES modules against a real DOM/localStorage via jsdom rather than skipping runtime testing — this caught and fixed three real bugs: search failing to match Greek-letter terms like Cohen's κ, a "Study Days" counter that never counted the first visit, and Practice Again/Retry buttons that silently did nothing because they relied on a hash that never changed.

Evaluating GenAI Workflows — Prompt Optimization

A guided hands-on exercise: build an LLM-powered aspect + sentiment classifier for customer reviews of a sneaker line, then use DeepEval's GEPA optimizer to automatically improve the classification prompt and measure the gain with F1 scoring.

Tools: Python · OpenAI API · DeepEval (Golden datasets, GEPA prompt optimization) · scikit-learn (F1 evaluation) · pandas

+ Add spec 💻 Repo + Add demo

The Problem

Case-study brief: Nima, a global sportswear brand, launched a new sneaker line that drove strong early sales but also a rise in product returns. Star ratings alone couldn't explain why customers were dissatisfied — the real signal was buried in free-text reviews mentioning specific product aspects like sizing, comfort, durability, color, design, and price/value. The exercise: build a proof-of-concept that identifies the aspect each review is about and classifies the sentiment toward it, then evaluate and systematically improve that classifier.

My Role & Approach

Product thinking

Treated prompt quality as something to measure and iterate on rather than eyeball — held out a true test set from the start, and used gold-labeled data specifically to validate whether a prompt-optimization pass actually generalized, versus just overfitting to the examples it saw.

Build approach

Built a baseline (v1) system prompt classifying each review's aspect and sentiment via the OpenAI API, scored it against the gold training labels with aspect F1, sentiment F1, and joint F1. Then ran DeepEval's GEPA optimizer over a Golden dataset to automatically evolve the prompt, re-scored the optimized (v2) prompt on the same training set, and finally ran v2 once on the held-out test set to check whether the improvement generalized to unseen data.

What It Does

  • Classifies each customer review into a product aspect (sizing, comfort, durability, color, design, price/value) and a sentiment (positive/negative/neutral)
  • Scores predictions against gold labels with aspect F1, sentiment F1, and joint F1
  • Runs DeepEval's GEPA prompt optimizer to automatically rewrite the classification prompt for better accuracy and consistency
  • Compares baseline vs. optimized prompt performance side-by-side on the training set
  • Validates the optimized prompt once on a held-out test set to check for overfitting

Outcome

GEPA-based prompt optimization improved classification performance over the baseline prompt, particularly for sentiment prediction and joint aspect-sentiment accuracy. The optimized prompt held up on the unseen test set, indicating the improvement generalized rather than overfitting to the training data.

AI for Research Proposal Automation

Case-study brief: a mid-sized research university's grants office spends 110–140 hours per federal funding announcement (NOFO) searching a 3,000-document internal archive and drafting an initial concept note. This pipeline automates the search-and-first-draft step with retrieval-augmented generation.

Tools: Python · LangChain · Chroma (vector store) · OpenAI (LLM + text-embedding-3-small embeddings) · tiktoken

+ Add spec 💻 Completed notebook 💻 Notebook (full code) 💻 Notebook (low code) 📄 Sample NOFO 📝 Generated concept note 📊 Rubric evaluation

The Problem

A NOFO (Notice of Funding Opportunity) spells out a funding program's priorities, eligibility, and deadlines. Proposal development draws on an internal corpus of ~3,000 papers, technical reports, and past proposals accumulated over 10 years and scattered across shared drives in inconsistent formats — and federal agencies have been shortening response windows, compressing exactly the phase this project targets.

My Role & Approach

Product thinking

Framed as a JHU coursework case study modeled on a fictional research university (MSRU), scoped to the highest-leverage manual step — connecting a new funding opportunity to relevant prior internal work — rather than automating grant-writing end to end.

Build approach

Extracts the funding topic from the NOFO, embeds and retrieves the most relevant prior papers from a Chroma vector store, ranks them by retrieved-chunk frequency, summarizes the top papers, generates five funding-aligned research ideas grounded in that evidence, drafts a first concept note against the supplied proposal template, and scores the draft with an LLM-as-judge rubric modeled on NIH review criteria (Innovation, Significance, Approach, Investigator Expertise — each scored 1–5 with justification, strengths, weaknesses, and recommendations).

What It Does

  • Extracts the funding topic and requirements from an input NOFO PDF
  • Chunks and embeds the internal paper archive into a Chroma vector store
  • Retrieves and ranks the papers most relevant to the NOFO topic
  • Generates five funding-aligned research ideas grounded in the shortlisted papers
  • Drafts a first-pass concept note from a chosen idea, using the supplied proposal template, and exports it to PDF
  • Evaluates the draft against an LLM-based scoring rubric

Outcome

Completed the notebook and ran it end-to-end against an NIMH digital mental health NOFO. The pipeline produced a concept note — "Webcam-Signal-Triggered Support During Digital Mental Health Treatment" — grounded in the retrieved archive papers, which the rubric scored Innovation 4/5, Significance 4/5, Approach 2/5, and Investigator Expertise 1/5. The low scores are an honest signal rather than a failure: the judge flagged that the draft leaves the platform, target population, trigger algorithm, and team unspecified — exactly the details a human grant writer still has to supply on top of the AI first draft.

Booking & Scheduling System (n8n)

The ThuWork website had no working way to book a call — just a front-end-only form and a mailto link. Rather than bolt on a third-party widget, this builds ThuWork's own advertised "Scheduling & Bookings" module once, runs it live on ThuWork's site, and structures it so it can be cloned and rebranded for clients.

Tools: n8n (self-hosted) · Google Calendar, Gmail & Sheets · Docker Compose (n8n + Postgres 16 + Caddy 2 / Let's Encrypt) · Hetzner Cloud VPS · Vanilla JavaScript (fetch + AbortController)

📄 Build plan & issue log ✅ Testing log 💻 Infra config + Add demo

The Problem

"Scheduling & Bookings" is one of ThuWork's advertised Business Suite modules ("a booking page that syncs your calendar and follows up automatically on no-shows"), yet ThuWork's own site couldn't take a booking. The goal was to build the real module, dogfood it on ThuWork first, and make it a product that's cheap to clone per client — not a one-off integration.

My Role & Approach

Product thinking

Chose a hybrid architecture: a booking widget styled to match the existing site, talking to a self-hosted n8n instance that owns all backend logic — consistent with n8n already being ThuWork's standard automation layer. Every workflow is parameterized through one top-of-workflow Config node so cloning for a client is "edit one node," and Google Sheets was picked for lead logging because a non-technical client can read it. Flagged openly that no-show detection is inferred (a calendar can't tell you whether a call happened) rather than overpromising — the same limitation Calendly has.

Build approach

Replaced the mock contact form with a native date input and a time-slot dropdown populated live from n8n (the server is the single source of truth for availability), with timeout, loading, success, and mailto-fallback states. Built three n8n workflows — Availability Check, Booking Intake (shared-secret header check, defensive re-check of the slot, calendar event with the client as attendee, confirmation email, Sheet row), and Reminder + No-show Follow-up on a polling schedule rather than fragile multi-day Wait nodes. Then stood up production n8n from scratch on a Hetzner VPS behind Caddy with automatic HTTPS, and logged every gotcha hit along the way as a resale runbook.

What It Does

  • Shows only genuinely open half-hour slots for a chosen date, computed from Google Calendar free/busy against configured business hours
  • Books the slot: creates a calendar event with the client invited, sends a confirmation email, and logs the lead to a Google Sheet
  • Rejects unauthorized requests (401) and double-bookings of the same slot (409)
  • Sends reminders and no-show follow-ups on a schedule, tracked via Sheet status columns
  • Runs in production at a dedicated n8n subdomain on a Dockerized n8n + Postgres + Caddy stack

Outcome So Far

Availability and Booking Intake workflows pass all tests (slot filtering, auth rejection, successful booking, double-booking guard), and the full production loop — website widget → production n8n → Google Calendar / Gmail / Sheets — has been verified end-to-end. The Reminder + No-show workflow is built and debugged on local n8n but not yet given a final pass or migrated to production.

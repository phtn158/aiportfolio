Personal Finance Coach & Spending Analyzer

A Python-based finance coach for a fictional fintech (ClearLedger Inc.) that auto-categorizes transactions with an LLM, predicts days-to-spending-limit, and coaches users toward better spending decisions conversationally.

Tools: Python · LLM API (few-shot transaction categorization) · Regression model (spend prediction) · Interactive dashboard · Conversational AI coach

📄 Spec 💻 Repo + Add demo

The Problem

Case-study brief: ClearLedger Inc., a pre-Series-A fintech with 55,000 users, was losing 71% of users after their second session because the app required manually tagging 60–150 transactions before delivering any insight. The assignment: design a Personal Finance Coach that eliminates that manual step entirely, under real constraints — limited ML expertise, no labeled training data, and a strict cost budget — while getting a user to their first real insight in under five minutes.

My Role & Approach

Product thinking

Scoped the build around four AI capabilities that had to work as one coherent pipeline rather than isolated exercises: LLM classification, interactive visualization, regression-based prediction, and stateful conversational memory. Every design choice (few-shot prompts instead of a trained classifier, per-user regression instead of a cross-user model) was made to work around the "no labeled data / limited ML expertise" constraints, not just picked for its own sake.

Build approach

Ingests and normalizes a raw transactions CSV, enriches it with MCC-code categories, then re-classifies each transaction into a small fixed taxonomy via a few-shot LLM prompt (batched/cached by merchant to control cost). That feeds an analytics layer (spend aggregation + z-score anomaly detection) which powers both a live spending dashboard and a per-user regression model predicting days remaining until the user's self-set discretionary limit. Ranked, category-level spending-reduction suggestions and the prediction are then grounded into a multi-turn conversational coach via system-prompt injection, so the coach cites real numbers instead of inventing them.

What It Does

  • Ingests a bank-statement CSV and categorizes every transaction with an LLM — no manual tagging required
  • Renders an interactive spending dashboard (category breakdown, spend trend, anomaly markers, limit burn-down)
  • Predicts days remaining before the user hits their discretionary spending limit, via a regression model trained on their own transaction history
  • Surfaces ranked, category-level suggestions for extending that runway (e.g. "cutting dining 20% adds 2 days")
  • Answers follow-up questions through a multi-turn conversational coach grounded in the actual prediction and spend data

Aspect-Based Sentiment Classification

An ABSC pipeline that classifies sentiment toward specific aspects of a review (e.g. food vs. service) via LLM prompting through LangChain, rather than training a task-specific classifier — benchmarked on the SemEval-2014 Task 4 dataset.

Tools: Python · LangChain · Hugging Face Transformers (Qwen2.5-0.5B-Instruct) · pandas · scikit-learn · SemEval-2014 laptop/restaurant review dataset

📄 Spec 💻 Repo / README + Add demo

The Problem

Aspect-Based Sentiment Classification identifies sentiment toward individual aspects within a piece of text rather than one overall label — e.g. in "the food was delicious, but the service was slow," sentiment toward food is positive while service is negative. That level of detail is far more actionable for businesses than document-level sentiment. ABSC is traditionally handled with fine-tuned classifiers (BERT-style models); this project instead explores how far a general-purpose LLM, driven purely by prompt design, can get on the same task.

My Role & Approach

Product thinking

Chose a small, locally-run instruction-tuned model (Qwen2.5-0.5B-Instruct) over a larger one deliberately — the exercise's goal was understanding how each pipeline component works end-to-end, not maximizing accuracy, so faster iteration won out over model size.

Build approach

Wrapped a Hugging Face text-generation pipeline in LangChain's HuggingFacePipeline, paired it with a few-shot PromptTemplate that constrains output to a fixed sentiment label set, and built a custom output parser (regex extraction + ast.literal_eval, wrapped in a RunnableLambda) to safely pull clean (aspect, sentiment) tuples out of noisy raw generations. The three pieces are composed into a single chain with LangChain's pipe operator.

What It Does — in progress

  • Loads and validates the SemEval-2014 laptop and restaurant review datasets
  • Runs a few-shot prompt through the LangChain chain to extract aspects and classify sentiment (positive/negative/neutral/conflict) per aspect
  • Parses raw LLM output into clean, validated (aspect, sentiment) tuples
  • Iterates over the deduped review set with progress tracking (tqdm), collecting predictions per review

Still to build: graceful handling of failed/unparseable generations, attaching gold labels alongside predictions, and the scikit-learn evaluation layer (precision/recall/F1, confusion matrix) that scores the pipeline against ground truth.

CI/CD Failure Log Intelligence

A prompt-engineering pipeline that reads a failed CI/CD build log, sanitizes it, classifies the failure, and explains it in plain English with a concrete fix — evaluated with an LLM-as-judge instead of word-overlap metrics.

Tools: Python · Prompt engineering · PII sanitization · LLM-as-judge evaluation (+ ROUGE / BERTScore)

+ Add spec 💻 Repo + Add demo

The Problem

CI/CD pipelines fail across many different tools — Jenkins, GitHub Actions, GitLab CI, CircleCI, Azure DevOps — each producing noisy, inconsistently formatted logs. Engineers lose time just figuring out what broke before they can even start fixing it. The goal: cut time-to-diagnosis to under five minutes by having an LLM read the failed-build log and explain it, without ever exposing raw log contents (which can contain secrets/PII) directly to the model.

My Role & Approach

Product thinking

Set hard rules up front rather than letting the LLM free-form: raw logs are never sent to the model unsanitized, classification must use only a fixed label set, and summaries must follow a fixed output structure — so results stay consistent and machine-parseable across the whole dataset. Judged usefulness by task metrics (accuracy, actionability) rather than word-overlap metrics, since a technically-similar-sounding summary isn't the same as a useful one.

Build approach

Built a pipeline that sanitizes each raw log first (strips long token-like strings, file paths, and KEY=VALUE env-var secrets), classifies the failure against a fixed taxonomy with a majority-vote consistency check across repeated model calls, then generates a plain-English summary with a concrete fix. An LLM-as-judge scores each summary for accuracy and actionability alongside ROUGE/BERTScore, and a separate script automatically reruns and regenerates any summary the judge flags as not actionable.

What It Does

  • Ingests failure logs from a multi-CI-tool dataset (Jenkins, GitHub Actions, GitLab CI, CircleCI, Azure DevOps)
  • Sanitizes each log — strips tokens, file paths, and env-var secrets — before anything reaches the model
  • Classifies each failure into a fixed label set, with a consistency check across repeated model calls
  • Summarizes the failure in plain English with a concrete suggested fix, in a fixed output structure
  • Scores summary quality with an LLM-as-judge (accuracy + actionability) alongside ROUGE/BERTScore
  • Automatically reruns and regenerates summaries the judge flags as low-actionability

Outcome

Ran end-to-end across the failure-log dataset, producing judged accuracy/actionability scores and ROUGE/BERTScore metrics per sample.

Applied GenAI Study Hub

A personal study site — dictionary, spaced-repetition flashcards, quizzes, a formula/code reference, and a weak-spot dashboard — built from the lecture slides of an Applied Generative AI program, organized around what you'd actually do with the material rather than the order it was taught in.

Tools: HTML/CSS/JavaScript (ES modules, no framework) · localStorage (SM-2-style spaced repetition) · Python (PDF-to-content pipeline, content validation)

📄 Spec 📝 Build notes 🔗 Live site

The Problem

Studying from a stack of lecture-slide PDFs doesn't build retention — concepts are scattered across multiple decks, formats are inconsistent, and there's no mechanism for noticing what you keep getting wrong. This project turns those PDFs into one structured, testable, self-updating study surface for a single learner (me) working through an Applied Generative AI program, meant for reviewing and self-testing between lectures on a phone or laptop without setting up an account anywhere.

My Role & Approach

Product thinking

Deliberately scoped out accounts, login, multi-device sync, and any runtime LLM calls — all dictionary, flashcard, and quiz content is authored once from source material and stored statically, since the real requirement is one learner reviewing on whatever device they're on right now, not a multi-user product. The content structure itself went through revision: mirroring the program's actual lecture order first felt logical but read like a syllabus, so it was reorganized task-flow-first — six repeatable task-type modules (Classification, Summarization, QA, Translation, Code Generation, Speech-to-Text), each following the same pattern, with shared prerequisites up front and cross-cutting/reference material pushed to the end.

Build approach

Static HTML/CSS/JS with no build step; a single content.json is the source of truth that every view (dictionary, flashcards, quiz, formulas, dashboard) renders from, so adding a concept automatically makes it searchable and flashcard-eligible without per-view wiring. Chose a simplified SM-2 spaced-repetition algorithm (the same family Anki uses) over a binary right/wrong toggle so the app can track an ease factor and miss count per card and actually prioritize what needs review. The content pipeline extracts new lecture PDFs with pdftotext, then hand-authors entries into the shared schema, validated by script for duplicate IDs and valid quiz answer indices before merging.

What It Does

  • Dictionary of every concept from the program (165 entries as of the latest update), each with a plain-language "explain like I forgot everything" one-liner above the formal definition, tagged by category and by the Python package that implements it
  • Flashcards with SM-2-style spaced repetition — cards marked "Missed it" or "Shaky" resurface more often; consistently-correct cards space out further
  • Multiple-choice quizzes per module, with an explanation shown after each answer
  • A formulas & code reference pulling every formula into one lookup page
  • A "My Progress" weak-spot dashboard aggregating flashcard and quiz misses into a focus list
  • Site-wide search, and a weekly scheduled workflow that checks for new lecture material and proposes dictionary/flashcard/quiz additions in the existing schema

Outcome So Far

Currently 165 dictionary entries, 84 flashcards, and 58 quiz questions across 12 modules, spanning the original NLP/LLM curriculum plus a Claude-specific practitioner track folded in through the first real run of the weekly content-update workflow. Since a real browser wasn't available in the build environment, the app was tested by running its actual ES modules against a real DOM/localStorage via jsdom rather than skipping runtime testing — this caught and fixed three real bugs: search failing to match Greek-letter terms like Cohen's κ, a "Study Days" counter that never counted the first visit, and Practice Again/Retry buttons that silently did nothing because they relied on a hash that never changed.
